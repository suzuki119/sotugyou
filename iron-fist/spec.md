## 1. プロジェクト概要

Mac のカメラ映像から両手を認識し、手の位置と形をロボットの操縦に使う 3D シューティングゲームを、Webブラウザ上で制作する。

プレイヤーは巨大ロボットのコックピットに搭乗しており、空中に「見えない操縦グリップ」を両手で握って機体を動かし、敵を撃つ。

### 制作理由

これまでに学んだ中で特に「見て驚ける」と感じた、Webサイト上での3D表現と手を読み取るライブラリを組み合わせる。機能（手認識・ゲームシステム）とデザイン（3Dモデル・UI）の両面から1つのゲームとして仕上げる。

### 重視すること

- 手認識の精度
- 操作の分かりやすさ
- 遅延の少なさ
- ゲームとしての面白さ
- 初めてのユーザーでも理解できるUI
- 展示用Mac + Chrome での安定動作

## 2. ゲーム企画

### 2.1 コンセプト

巨大ロボットに乗り込み、両手で操縦グリップを握って戦う。
マウスやコントローラーではなく「自分の手で操縦している」感覚を体験の中心に置く。

### 2.2 手認識を使う必然性

マウスやキーボードより面白くなる理由を、以下の3点とする。

1. **操縦している没入感**：空中のグリップを握る動作が、そのままロボットの操縦桿を握る動作になる。
2. **両手を同時に使う体験**：本物のコックピットのように、左右の手で別々の操作を同時に行う。
3. **見た目の驚き**：何も持たずに手を動かすだけで、画面の機体が反応する。

機能を追加するときは「この3点を強めるか」を判断基準にする。

### 2.3 1プレイの流れ（3〜5分）

```
タイトル
  ↓
カメラ許可の説明 → 許可
  ↓
キャリブレーション（両手の基準位置を登録）
  ↓
操作チュートリアル（照準・射撃・移動を1つずつ試す）
  ↓
ステージ開始：雑魚敵との戦闘
  ↓
ボス戦
  ↓
ボス撃破 → クリア / HP0 → ゲームオーバー
  ↓
リザルト（スコア・タイム等）→ リトライ / タイトル
```

時間配分の目安（要調整）：

| パート                             | 目安     |
| ---------------------------------- | -------- |
| キャリブレーション・チュートリアル | 〜1分    |
| 雑魚戦                             | 1.5〜2分 |
| ボス戦                             | 1〜2分   |

### 2.4 勝敗条件

- **クリア**：ボスを撃破する
- **ゲームオーバー**：機体HPが0になる
- **スコア**：撃破数、クリアタイム、残りHP などから算出（詳細は Phase 4 で調整）

### 2.5 敵

| 種類   | 数       | 備考                                   |
| ------ | -------- | -------------------------------------- |
| 雑魚敵 | 2〜3種類 | 動き・攻撃方法を変えて差別化する       |
| ボス   | 1体      | クリア条件。攻撃パターンを複数持たせる |

### 2.6 難易度・リプレイ性

- 展示で初めて遊ぶ人でもボスまで到達できる難易度を基準にする。
- リザルトでスコアやタイムを表示し、もう一度挑戦したくなるようにする。
- 難易度の詳細は Phase 4 で、実際に第三者に遊んでもらって調整する。

## 3. 操作仕様（ジェスチャー設計）

### 3.1 基本方針

- ジェスチャーは増やしすぎない。初期バージョンは以下の操作のみとする。
- 両手とも「基準位置（ニュートラル）」からのずれで操作する。基準位置はキャリブレーションで登録する。

### 3.2 右手：照準・射撃

| 操作           | 手の動き                              | ゲーム入力                                                                 |
| -------------- | ------------------------------------- | -------------------------------------------------------------------------- |
| グリップを握る | 👍の形（4本指を握り、親指を立てる）   | 右グリップ有効                                                             |
| 照準 左右      | 基準位置から手を左右に動かす          | 照準の左右                                                                 |
| 照準 上下      | 基準位置から手を奥に押す / 手前に引く | 照準の上下（初期案：奥＝下、手前＝上。操縦桿方式。反転設定は検証で決める） |
| 射撃           | 👍の状態から親指を閉じる              | 親指を閉じている間、連射                                                   |
| 射撃停止       | 親指を再び立てる                      | 射撃停止                                                                   |

### 3.3 左手：移動（バーチャルスティック）

| 操作           | 手の動き                                 | ゲーム入力     |
| -------------- | ---------------------------------------- | -------------- |
| グリップを握る | 手を握る（右手と同じ握り形を基本とする） | 左グリップ有効 |
| 移動           | 基準位置からのずれの方向・量             | 移動方向・速度 |
| 停止           | 基準位置に戻す（デッドゾーン内）         | 停止           |

### 3.4 手が外れたとき

- 片手でもグリップが外れた・認識できなくなった場合は、その手の入力を0にする（照準停止・射撃停止・移動停止）。
- 両手が一定時間認識できない場合は一時停止し、手を映すよう案内する。

### 3.5 要検証の操作項目

- **奥・手前の判定**：カメラは奥行きを直接測れない。手の大きさ（手首〜中指付け根の距離など）やランドマークの z 値から推定する。ブレやすいため Phase 1 で最優先に検証する。安定しない場合の代案は「画面上での手の上下」で照準の上下を操作する方式とする。
- **親指を閉じる判定**：拳の向きによって親指が隠れ、判定が途切れる可能性がある。ヒステリシスと短い猶予時間で、連射が勝手に止まったり始まったりしないようにする。
- **照準の方式**：手のずれを「照準位置」として扱うか、「照準（視点）の回転速度」として扱うかを試作で比較する。
- **左手スティックの軸**：前後移動を「奥・手前」で取るか「画面上の上下」で取るかを検証する。
- **疲労**：3〜5分間、両手を空中に上げ続けて疲れないか。

## 4. 手認識技術

### 4.1 候補

| 候補                                      | 概要                                                                      |
| ----------------------------------------- | ------------------------------------------------------------------------- |
| ml5.js（handPose）                        | 企画書で予定していたライブラリ。中身は MediaPipe 系のモデル。書き方が簡単 |
| MediaPipe Hand Landmarker（Tasks Vision） | MediaPipe を直接使う。設定の自由度や速度調整がしやすい                    |

試作（カメラ・ランドマーク表示）はすでに動作している。この試作をもとに、両方を同じ条件で比較して決定する。

### 4.2 比較項目

- 推論速度（展示用 Mac + Chrome での実測 FPS）
- 両手同時認識の安定性
- 左右の手の識別精度
- 奥行き（z 値）の取得可否と安定性
- 親指の開閉など、細かい指の形の判定しやすさ
- GPU（WebGL / WebGPU）対応
- npm で導入できるか、Vite との相性
- モデルファイルの読み込み方法（オフラインの展示会場で動かせるか）
- ライセンス、今後の保守性

※ライブラリは制作時点の最新の公式ドキュメントを確認してから決定する。廃止された API や古い実装方法は使わない。

### 4.3 オフライン動作

展示会場のネットワーク環境に依存しないよう、モデルファイル・ライブラリはローカルに同梱して読み込めるようにする（CDN に依存しない）。

## 5. カメラ

### 5.1 カメラ権限

- `navigator.mediaDevices.getUserMedia()` でカメラを取得する。
- カメラ拒否・カメラなし・他アプリ使用中の場合は、それぞれ解決方法を案内する（23. エラー処理を参照）。

### 5.2 セキュリティ

- カメラ利用には Secure Context（localhost または HTTPS）が必要。
- 展示は Vite の開発サーバーまたはビルド後のローカル配信（localhost）で動かす。
- Web 公開する場合は HTTPS 環境が必須（公開は未定）。

### 5.3 カメラUIの流れ

1. カメラを使う理由の説明（映像は保存・送信しないことも明記）
2. カメラ開始ボタン
3. ブラウザのカメラ許可
4. 両手をカメラに映す
5. 認識開始

### 5.4 カメラ映像の扱い

- **ゲーム中はカメラ映像を表示しない。** ゲーム画面（コックピット）に集中させる。
- 代わりに HUD で以下を常に示す（24. デザイン方針を参照）。
  - 左右それぞれの手の認識状態
  - グリップを握っているか
  - 基準位置からのずれ（スティックの倒れ具合）
- キャリブレーション画面とデバッグ画面では、ランドマーク表示を使ってよい。

## 6. 手認識データの設計

認識ライブラリの結果をそのままゲーム操作に使わず、ゲーム側で扱いやすい独自の入力データへ変換する。

```
Camera
  ↓
Hand Tracking（ml5.js or MediaPipe）
  ↓
Landmarks（21点 × 左右）
  ↓
Landmark Processor（平滑化・座標変換・奥行き推定）
  ↓
Gesture Detector（グリップ判定・親指判定・オフセット計算）
  ↓
Input Manager（抽象化された入力）
  ↓
Game Logic
```

使用する情報：

- 手首・各指の関節のランドマーク座標
- 左手 / 右手の識別
- 検出信頼度
- 手の大きさ（奥行き推定用）

## 7. ジェスチャー判定の安定化

| 手法         | 適用先                                                               |
| ------------ | -------------------------------------------------------------------- |
| デッドゾーン | 照準・移動の基準位置付近の小さな揺れを無視する                       |
| 平滑化       | 位置・奥行きを過去数フレームで平滑化する（遅延とのバランスを調整）   |
| ヒステリシス | グリップ・親指の ON/OFF の境界で状態が高速に切り替わらないようにする |
| 猶予時間     | 親指が一瞬隠れても、すぐには射撃を止めない                           |
| 信頼度       | 信頼度が低いフレームは入力として使わない                             |

※射撃は「押している間」の入力なので、クールダウンではなくヒステリシスと猶予時間で安定させる。

---

## 8. ゲーム入力の抽象化

手認識処理とゲーム本体を直接結合しない。ゲーム側は以下の抽象化された入力だけを受け取る。

```js
input = {
  aimX, // -1〜1 照準の左右
  aimY, // -1〜1 照準の上下
  fire, // boolean 射撃中か
  moveX, // -1〜1 左右移動
  moveY, // -1〜1 前後移動
  rightGrip, // boolean 右グリップを握っているか
  leftGrip, // boolean 左グリップを握っているか
  rightTracked, // boolean 右手を認識しているか
  leftTracked, // boolean 左手を認識しているか
};
```

- 展示版の入力は手認識のみ。
- **開発用にキーボード入力（デバッグ用）を Input Manager に実装しておく。** 手を使わずにゲームロジックをテストするためのもので、展示版では無効にする。

## 12. キャリブレーション

カメラ位置や体格の違いを吸収するため、ゲーム開始前に両手の基準位置を登録する。

1. 「両手でグリップを握るように、手を構えてください」と案内する
2. 両手の位置と手の大きさ（奥行きの基準）を一定時間取得し、平均を基準値にする
3. 基準値からのずれを照準・移動の入力に変換する

リトライ時はキャリブレーションを省略できるようにする（同じ人が続けて遊ぶ場合）。

## 15. パフォーマンス

確認項目：

- 描画 FPS、手認識の推論 FPS
- CPU / GPU / メモリ使用量
- カメラ解像度
- モデルサイズ、初回ロード時間

方針：

- 描画（60FPS 目標）と手認識（15〜30FPS 目標）の更新頻度を分離する。
- Three.js 側の 3D 描画と手認識が同じ Mac の GPU を使うため、両方を動かした状態で計測する。
- 試作では「描画 60fps / 推論 23fps」程度を確認済み。ゲーム描画を追加した後も維持できるか確認する。

---

## 16. 認識精度の検証

以下の環境でテストする。

- 明るい部屋 / 暗い部屋
- 背景が複雑 / 単純（**展示会場では後ろを人が通る想定**）
- 手がカメラに近い / 遠い
- 手が画面外に出る、両手が重なる
- 素早い動き
- 他の人の手が映り込む

「認識できるか」だけでなく、**ゲーム操作としてストレスなく使えるか** を評価する。

## 17. UX設計

初めて遊ぶ人が説明なしでも操作を理解できることを目標とする。

```
① カメラを許可
  ↓
② 両手をカメラに映す
  ↓
③ グリップを握るように構える →「認識しました」
  ↓
④ チュートリアル：右手で照準 → 親指で射撃 → 左手で移動
  ↓
⑤ ゲーム開始
```

- 操作説明は文章だけに頼らず、手のアイコン・アニメーション・矢印・色やエフェクトで示す。
- 展示ではパンフレット・パネルでも操作方法を案内する。

## 18. 代替操作

- 展示版は手認識のみとし、マウス・キーボードの代替操作は用意しない。
- 開発用のキーボード入力のみ実装する（8. を参照）。
- カメラ拒否・認識失敗時の案内は必ず用意する。

## 19. 対応環境

- **対象：展示用の自分の Mac（内蔵カメラ）+ Google Chrome のみ。**
- 他のブラウザ・PC・スマートフォンは対象外。
- Web 公開する場合は、その時点で PC の Chrome / Edge を対象に追加検討する。

## 20. セキュリティ・プライバシー

- カメラ映像はブラウザ内だけで処理し、サーバーへ送信しない。
- 映像・手の認識データは保存しない。
- 外部 API へ映像を送信しない。
- カメラ許可の前に、上記をユーザーに明示する。

## 21. 開発フェーズ

展示（2027年1月）から逆算した目安。日付は仮で、進み具合に合わせて見直す。

| Phase                | 内容                                                              | 目安          |
| -------------------- | ----------------------------------------------------------------- | ------------- |
| 1 技術検証           | ライブラリ比較、両手認識、奥行き推定、親指判定の検証              | 10月中旬      |
| 2 入力システム       | Input Manager、キャリブレーション、テスト画面                     | 10月下旬      |
| 3 プロトタイプ       | グレーボックスで機体・照準・射撃・雑魚敵・ボス・HP・勝敗          | 11月中旬      |
| 4 ゲーム性調整       | 操作感・難易度・疲労の調整、第三者テスト                          | 11月下旬      |
| 5 UI・演出・アセット | Blender モデル差し替え、HUD、チュートリアル、エフェクト、サウンド | 12月          |
| 6 実機テスト         | 展示環境に近い条件でテスト、最終調整                              | 12月下旬〜1月 |

※Blender のモデル制作は Phase 3 と並行して進める。

### Phase 1：技術検証

最初にゲームを作らない。以下だけを実装・検証する。

```
カメラ起動 → 両手認識 → ランドマーク表示 → 左右判定
  → 👍グリップ判定 → 親指開閉判定 → 奥行き推定
```

ここで「両手操作が実用的な速度・精度で動くか」を判断する。特に奥行き推定が使えるかで、照準の上下の方式を確定する。

### Phase 2：入力システム

```
右手 左右       → aimX
右手 奥・手前   → aimY
右手 親指を閉じる → fire
左手 ずれ       → moveX / moveY
```

テスト画面（照準カーソルと移動ベクトルの表示のみ）で操作感を確認する。

### Phase 3：ゲームプロトタイプ

機体、照準、射撃、雑魚敵、ボス、HP、クリア / ゲームオーバーを実装する。グラフィックは作り込まない。

### Phase 4：ゲーム性の調整

- 操作が難しすぎないか
- 誤認識が多くないか
- 3〜5分で手が疲れないか
- 遅延を感じないか
- 手で操縦する意味を感じられるか
- 何度も遊びたくなるか

### Phase 5：UI・演出

タイトル、チュートリアル、HUD、エフェクト、サウンド、リザルト、リトライ、エラー画面を実装し、Blender のモデルに差し替える。

### Phase 6：実機テスト

展示用 Mac で、照明・背景を変えてテストする。第三者に説明なしで遊んでもらい、操作を理解できるか確認する。

## 22. エラー処理

技術的なエラーをそのまま表示せず、具体的な解決方法を示す。

| ケース               | 表示例                                                                                            |
| -------------------- | ------------------------------------------------------------------------------------------------- |
| カメラが拒否された   | 「カメラを使用できませんでした。Chrome のアドレスバー左のアイコンからカメラを許可してください。」 |
| カメラが存在しない   | 「カメラが見つかりませんでした。」                                                                |
| 他アプリが使用中     | 「カメラが他のアプリで使用中です。他のアプリを閉じてから再度お試しください。」                    |
| 手を認識できない     | 「両手をカメラに映してください。」                                                                |
| 片手を見失った       | HUD でその手の表示を赤くし、入力を止める                                                          |
| 両手を見失った       | 一時停止して案内を表示                                                                            |
| 3人以上の手が映った  | 「カメラに映る手を2本にしてください。」                                                           |
| モデルの読み込み失敗 | 「読み込みに失敗しました。ページを再読み込みしてください。」                                      |
| 非対応ブラウザ       | 「Google Chrome でお楽しみください。」                                                            |
| 処理が重い           | カメラ解像度・推論頻度を自動で下げる（検討）                                                      |

## 23. デザイン方針

世界観：巨大ロボットのコックピット。ただし、通常のゲーム以上に **「何をすればいいか分かるUI」** を優先する。

カメラ映像を表示しないため、HUD で以下を視覚的に伝える。

- 左右の手の認識状態（認識中 / 見失い）
- グリップを握っているか
- 照準の位置、射撃中か
- 左手スティックの倒れ具合
- 機体HP、ボスHP
- ゲーム状態（チュートリアル中、ボス戦など）

HUD はコックピットの計器・モニターとして世界観に溶け込ませる。デザインは Illustrator / Figma で作成する。

## 26. 展示

展示で用意するもの：

- ゲーム用 PC（自分の Mac + 内蔵カメラ）
- パネル
- ゲーム情報が書かれたパンフレット（操作方法の図解を含む）
- 飾り・グッズ（3D プリンター製）

ゲーム側で考慮すること：

- 来場者が順番に遊ぶため、リトライとタイトルへの戻りを素早くできるようにする。
- 放置されたらタイトルに戻る（アトラクトモード）を検討する。
- 会場の照明・背景で認識できるか、事前に確認する。

## 27. 完成条件

### 技術

- 展示用 Mac + Chrome で動作する
- 両手を同時に認識できる
- 照準・射撃・移動のジェスチャーをゲーム入力に変換できる
- 描画・認識ともに十分な速度で動作する
- ネットワークなしで動作する

### ゲーム

- タイトルからボス戦、クリア / ゲームオーバーまで通して遊べる
- 1プレイ3〜5分に収まる
- スコアなどのゲーム性がある
- リトライできる
- 手で操縦する意味を感じられる

### UX

- 初めての人でも操作方法が分かる
- カメラ許可の説明がある
- 認識失敗時の案内がある
- 操作に大きなストレスがない、手が極端に疲れない

### 品質

- 展示環境に近い条件でテスト済み
- 大きな認識バグがない
- 極端な処理落ちがない
- GitHub でコード管理されている

## 29. AIへの開発指示

このプロジェクトで AI を利用する場合、以下の方針で支援する。

1. いきなり大量のコードを書かない。
2. まず要件・技術的な問題・実装方針を整理する。
3. 手認識部分とゲーム部分を分離する（ライブラリは `handTracker.js` に閉じ込める）。
4. 最新のライブラリ仕様を確認してからコードを書く。
5. 廃止された API や古い実装方法を避ける。
6. コードは可能な限り小さな単位で実装する。
7. 各段階で動作確認できる状態を維持する。
8. 認識精度・遅延・FPS など、実際の使用感を重視する。
9. セキュリティとカメラプライバシーを考慮する。
10. 技術的に可能かだけでなく、「ゲームとして面白いか」「2.2 の3つの理由を強めるか」を常に確認する。
11. 対象環境は展示用 Mac + Chrome に限定してよい。他環境への対応を勝手に広げない。

### 進め方

```
Step 1  既存の試作を確認する
Step 2  Vite + npm で最小構成のプロジェクトを作る
Step 3  カメラ取得を実装する
Step 4  両手認識を実装する（ml5.js / MediaPipe を比較）
Step 5  ランドマークを可視化する（デバッグ画面）
Step 6  グリップ・親指・奥行きの判定を実装・検証する
Step 7  キャリブレーションを実装する
Step 8  Input Manager に変換する（+ デバッグ用キーボード入力）
Step 9  Three.js でグレーボックスのゲームを作る
Step 10 ゲーム性・操作性を調整する
Step 11 Blender モデル・UI・演出を仕上げる
Step 12 展示環境で実機テストを行う
```
